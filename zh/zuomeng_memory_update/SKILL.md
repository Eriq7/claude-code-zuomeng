# zuomeng_memory_update（做梦 + memory 更新）

<!-- 设计依据见文末"出处"一节，哪些来自官方、哪些是作者加的都标了。 -->

**一句话：每周一次，替用户回头看一遍过去的对话，找出"同一个坑踩了好几次"，并把 memory 里过期的、错的清出来。** 所有改动先出清单，用户批准了才写。

为什么要这样做：单个 session 里的 agent 看不到别的 session，同一个错误会在新的上下文里再犯一遍；memory 是 agent 一点点写的，时间长了会有重复、矛盾和过期的条目，而 MEMORY.md 每次开会话都会加载（只加载前 200 行或 25KB）。官方 Dreams 就是为这两件事设计的，这个 skill 在本机照着它做。

## 范围

- 默认只处理一个主项目：把下面的 `<主项目目录名>` 换成你最常用的那个项目在 `~/.claude/projects/` 下的目录名（例：`-Users-you-code-myapp`）。memory 在 `~/.claude/projects/<主项目目录名>/memory/`。
- 其他项目只在用户同意时才加（第 1 步会问）。

回复用用户的语言，不用破折号。

## 流程

脚本是 `~/.claude/skills/zuomeng_memory_update/scripts/zuomeng.py`。目录名以 `-` 开头，所以参数必须写成 `--project=<目录名>`。

数据（复盘位置、快照、报告、修改记录）都放在 `~/.claude/zuomeng/`。

### 0. 引导块（用户可以改这一段）

**什么算重要：**
- 用户纠正 agent："不对""别这样""我说的是""你又……"
- 用户同一个要求说了不止一次（说明 memory 或 CLAUDE.md 里要么没有、要么没起作用）
- tool 反复失败、被用户拒绝、被 hook 拦下
- agent 违反了 memory 或 CLAUDE.md 里已经有的规则
- agent 反复去查同一件本该早就知道的事

**不算：** 一次性任务本身的难度、用户正常提的新需求、正常的探索和试错。

### 1. 先数一遍（决定要不要跑、跑哪些项目）

```bash
python3 -I ~/.claude/skills/zuomeng_memory_update/scripts/zuomeng.py scan
```

- 主项目的新 session 少于 5 个：告诉用户"这周只有 N 个新 session，按规则跳过"，**不要**记录复盘位置，结束。
- 其他项目新 session 达到 5 个：用普通文字列给用户，问要不要这次一起处理，不用多选框（容易点错）。每个项目写真实文件夹名和 session 数：目录名里的中文会变成一串 `-`，用 `ls` 对出真实名字。用户说要，那个项目就走同样的流程，清单单独标项目名。没达到门槛的不提。
- 脚本已经排除了最近 5 分钟还在写的会话（就是当前这个）。

### 2. 压缩 transcript

```bash
python3 -I ~/.claude/skills/zuomeng_memory_update/scripts/zuomeng.py digest --project=<目录名> --out <scratchpad>/zm_<日期>
```

脚本只读上次复盘位置之后的新 session（第一次是最近 7 天），每个压成一份短文本：用户的原话（不截断，纠正和重复要求都在里面）、助手的话（截短）、调用了什么 tool、tool 报错和被拒绝的记录。**密钥已在脚本里打码**，你写报告时也不要引用任何凭证，transcript 是明文存的，工具读到的密钥会混在里面。

它同时在输出目录里写 `batches.json`，把 session 按大小分成几批。

### 3. A 部分：找跨 session 的重复错误

主会话当 orchestrator。每一批派一个子 agent（并行，用 Agent 工具），不要自己读全部 digest，上下文装不下。给每个子 agent 的任务：

> 你在帮用户复盘用户和 Claude Code 的对话。下面是一批 session 的压缩记录（U=用户的原话，A=助手，T=tool 调用，X=tool 报错或被拒绝）。先读 `~/.claude/projects/<目录名>/memory/MEMORY.md` 和 `~/.claude/CLAUDE.md`，知道已经有哪些规则。然后读这批记录，找出下面这些情况（引导块里的"什么算重要"）。每一条候选按这个格式输出，一行一条，不要写别的：
> `类型 | 一句话描述这个错误 | session 前 8 位 | 证据原话（不超过 60 字，不含任何密钥） | 严重度 高/中/低 | 已有规则？（有:哪条 / 没有）`
> 类型只能是：纠正、重复要求、tool失败、违反已有规则、反复查同一件事。
> 严重度：高=让用户返工或险些出事；中=浪费一轮对话；低=小摩擦。
> 只报告你在记录里真的看到证据的，没有就输出"本批没有"。不要推测，不要凑数。

子 agent 一个个交回来时，每次只回用户一句"已收 N/总数"，不复述内容，收齐再合并。

收齐后你来合并：
1. 第一遍：把说的是同一件事的候选归成一组。
2. 第二遍：把没进组的候选逐条再对一遍，按"agent 做了什么事"归，别只看字面像不像。例："用户要在 GitHub 界面打开，agent 改去贴原文"和"用户要用 Chrome，agent 先去装 CLI"是同一组"用户指定的做法被换掉"。
3. **只保留出现在至少 2 个不同 session 的组**，一个 session 里出现再多次也只算一个 session，因为那更像是那次任务特有的麻烦。过门槛的全列，不设条数上限，清单开头写"共 N 组过门槛"。
4. 查已有办法：读 MEMORY.md 和 CLAUDE.md，这类问题用户已经定过解决办法的（例：回答太长，用户自己用 /jingjian 手动压），放进清单末尾"只列不改"，报次数，不提议改。
5. 排序：算分 = 出现的 session 数 × 严重度（高 3、中 2、低 1），分数写在次数列里当参考。清单顺序按你的建议排：改 > 可改可不改 > 不建议，每条标出建议和一句理由。用户要的是"你觉得该改的程度"，分数高但不值得改的排后面。
6. 每组写成一条提议：一句话规律、出现了几次/几个 session、两个例子（session 前 8 位加一句短引文）、原因属于哪种（memory 里没有 / memory 里有但没起作用 / skill 写得不清楚）、建议怎么改和拟写入的一两句话。**每条必须写明改在哪种地方、哪个文件**：全局 CLAUDE.md（哪一节）、memory（哪个文件，写全名并说一句这是管什么的 memory）、还是某个 skill（哪个 SKILL.md）；只说"加一条自查"这种不说位置的，用户看不懂。跨项目都可能遇到的事放 CLAUDE.md，只跟某件事、某门课有关的放 memory（例："打开付款页面前先问"别的项目也会遇到，放 CLAUDE.md）。不替用户决定。
7. 读 `~/.claude/zuomeng/changelog.md` 最上面一周（如果有）：上次改过的规则，这周还在犯的，单独标出来。这是检验这个 skill 有没有用的办法。

### 4. B 部分：核对 memory

自己读（不用子 agent，memory 文件不大）：MEMORY.md 加 memory 目录里全部文件。今天的日期用系统日期。检查：

- **大小：** MEMORY.md 多少行、多少字节，对比"前 200 行或 25KB"的加载上限。
- **过期：** 描述里写的期限、日期已经过了，而条目还是"待办/进行中/未结案"的。
- **核对事实：** 条目提到的文件路径、skill、命令、仓库是否还存在（用 ls、grep 查，不要凭印象）。
- **重复：** 两条讲的是同一件事。
- **矛盾：** 两条结论相反，或和最近 transcript 里用户的新说法相反。
- **已结案：** 标了"已结案/已买/已结"的条目，是否还值得占一行索引。
- **索引对不上：** MEMORY.md 里的链接指向不存在的文件，或描述和文件里的 description 不一致。最近一份 `~/.claude/zuomeng/reports/<日期>.md` 里写明"故意不进索引"的文件跳过，别再提议加回去。

注意区分：feedback 类（用户的偏好和做事规则）和 user 类不会因为"旧"就过期，只有它被新说法推翻才动；时间性强的 project 类和 reference 类才按过期来查。**不提议删文件**，除非能说清楚这个文件是什么、删了损失什么；有价值的先问用户。能"合并""更新一句""从索引移除但保留文件"的，优先这样提。

每条提议写：哪个文件、现在写的是什么、问题是什么（带依据）、建议改成什么。

### 5. 给用户看，逐条批准

两份清单编号（A1、A2……和 B1、B2……），每条带证据，用大白话写清两件事：现在会出什么事、改完会怎样；拟写入的原句写全，让用户不用追问就能判断。技术类的坑（shell 报错、工具失败）先说一句对用户有什么影响。能用表格就用表格。用户回"A1 A3 B2 通过，其余不要"这类话就够了。**没批准的一条都不改。**

清单最后单独写一句：这次的分析提示词（第 3 步给子 agent 的那段）不是官方的，如果找出来的东西不准，先怀疑它。

### 6. 写入（只写批准的）

1. 先快照：`python3 -I ~/.claude/skills/zuomeng_memory_update/scripts/zuomeng.py snapshot --project=<目录名>`，把输出的回滚命令记进报告。快照放在 memory 目录外面，不会被当成 memory 加载。
2. 按批准的条目改 memory 文件，同步改 MEMORY.md 的索引行。一条一条改，改完再检查 MEMORY.md 的行数和字节数。
3. 改 CLAUDE.md 或其他 skill：只有用户明确批准那一条才改。
4. 写报告到 `~/.claude/zuomeng/reports/<日期>.md`：批准了什么、拒绝了什么、快照位置、每条规律的出现次数。
5. 把 A 部分用户最终决定改了的，加一节到 `~/.claude/zuomeng/changelog.md` 最上面（文件不存在就新建）。每周一节，标题写日期和读了多少个 session；每条只写三点：**原本的错误**（一句话规律、几个 session、一个例子）、**为什么改**（用户原话加引号；是 agent 提的、用户只说了同意，就标"agent 提的"）、**改成什么**（哪个文件哪一节，加上改后的原文）。B 部分不记。下周第 3 步就读这里对比。
6. 记录复盘位置，值取 digest 输出里"最新到"的时间：`python3 -I ~/.claude/skills/zuomeng_memory_update/scripts/zuomeng.py mark --project=<目录名> --ts <那个时间>`。即使用户全部拒绝也要记，否则下周会把这批再读一遍。

### 7. 收尾

告诉用户：这次读了几个 session、提了几条、批准了几条、快照在哪。如果以后用户的 `/memory` 里出现了 Auto-dream 开关，B 部分会和内置功能重叠，提醒用户到时候再决定留哪个。

## 出处：哪些来自官方，哪些是加的

官方指 Anthropic 的 Dreams 设计（Lamis 的演讲稿，加 platform.claude.com/docs/en/managed-agents/dreams）。官方 Dreams 是 Managed Agents 的 API，读不了本机文件，所以这里是照它的做法在本机重做的。

| 设计点 | 出处 |
|---|---|
| 输入是现有 memory 加一批过去的 transcript，transcript 里连 tool 调用和元数据一起看 | 官方 |
| orchestrator 派一队子 agent 分析 | 官方（讲稿） |
| 可以写引导指令说明什么重要（第 0 步） | 官方 |
| 只有规律出现得够多才提修改 | 官方（讲稿） |
| 每条建议附 transcript 例子和出现次数 | 官方（讲稿） |
| 原 memory 不动，输出建议，人决定接受还是丢弃 | 官方 |
| 合并重复、过期或矛盾的换成最新值、提炼新发现 | 官方 |
| 保留版本（快照）和限制写权限（批准才写） | 官方（讲稿的 versioning 和 permissioning） |
| 每周一次；新 session 少于 5 个就跳过 | 加的（5 来自内置 auto-dream 的默认值） |
| "至少 2 个不同 session 才算规律" | 加的（官方只说"够普遍"） |
| 按 session 大小分批，而不是一个 session 一个子 agent | 加的（一周上百个 session，一个一个派太贵） |
| "上次复盘位置"记录；脚本打码密钥；不读正在进行的会话 | 加的 |
| 其他项目达到 5 个 session 时问用户要不要一起处理 | 加的 |
| 对比上周的修改记录（changelog.md），看改过的规则这周还犯不犯 | 加的 |
| 合并分两遍；已有办法的只列不改；清单按建议程度排；提议写明改在哪 | 加的 |
| **子 agent 的分析提示词（第 3 步）、memory 核对的检查项（第 4 步）** | **加的，官方没有公开** |
